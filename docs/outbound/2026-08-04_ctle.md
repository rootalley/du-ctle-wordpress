1. Platform conﬁguration is nearing completion

The technical foundation is complete. The site is live at https://ctle.dom.edu, running on
Kinsta, backed up daily, and deliberately hidden from search engines until we launch. Security
measures to protect the site from intrusion are in place.

Things still in progress:

• Email delivery will send WordPress notiﬁcations to users. We've created a ctle-
noreply@dom.edu system mailbox to separate notiﬁcations from human communication
at ctle@dom.edu. We're now working to connect that mailbox to WordPress and test the
notiﬁcations.

• Single sign-on (SSO) will be used when faculty need to log in, particularly to access
faculty discussion forums. I'm working actively with IT on this, and we need your
guidance on exactly who should be allowed into the restricted areas of the site (see
below).

• Canvas integration will let faculty connect from the LMS to WordPress using the same
CTLE icon currently shown to faculty on the global navigation menu. Our strategy to so
this is ready, but ﬁnishing this depends on SSO. Once SSO is done, this should only take
about an hour to ﬁnish.

2. IMPORTANT: Don't click the Push to Live button in MyKinsta!

The IT setups described above are all being done on the Live environment. This is by
necessity: WordPress notiﬁcations get sent from Live (not Staging), people SSO into Live (not
Staging), and so on. The consequence is that Live now holds a large amount of work that
Staging has never seen. Therefore, a Push to Live wouldn't just add your work to the site; it
would replace the Live site entirely and take the IT conﬁgurations with it.

3. We'll need to merge Staging ﬁles into Live, and we should do so soon

I see site construction underway on Staging that will need to be merged into the IT
conﬁguration on Live before launch. I propose doing this sooner rather than later so we can
complete the IT conﬁguration and we reduce risk of having any issues at go-live. I propose
these steps:

1. Amanda creates her user proﬁle on the Live environment. From MyKinsta, select the
Live environment, then click the Create admin and log in button.

2. Amanda/Persis will specify a maintenance window for Steven to do the merge. While
this is underway, you won't be able to make changes in either environment — anything
edited mid-copy may not survive. After the merge, Staging is frozen: any work done
there afterwards won't reach the Live site.

3. Steven will lock down the Live environment with a username and password, similar to
what we have in place on Staging. This will keep people from seeing the site until we've
got everything ready to go. I'll send you both the username and password for Live
separately, as I did for Staging.

4. Steven will create backups of both the Live and Staging environments.

5. Steven will export the WordPress ﬁles and settings from Staging and merge them into
Live.

6. Amanda can then resume development work but using the Live environment and NOT
Staging. (Everything from here to go-live would be on Live only.)

4. We need to specify who will be able to sign into the CTLE

To set up SSO, we need to specify who should be able to log in. I've done some preliminary
research on how other schools handle this, and here's the trend:

Who can log in is usually generous. Anyone who teaches or supports teaching is allowed: full-
time faculty, adjuncts, chairs, deans, provosts, emeriti still teaching, staff who are instructors of
record, librarians with teaching or instructional support roles, etc.

What happens inside the private area is then goverened with policy, not access permissions:

• Post a conﬁdentiality statement: The POD Network Ethical Guidelines for Educational

Developers is a common starting point that could be adapted to a forum context: nothing
posted will be used in evaluation, reappointment, promotion, or tenure; CTLE staff will
not report participation or content to chairs, deans, or the Provost; participation is
voluntary.

• Set an explicit expectation for administrators who do join: they participate as instructors

reﬂecting on their own teaching, and are bound by the same non-evaluative commitment.
• When users post, put a notice on the submission page to remind them that the forum is a
durable and searchable platform. Conﬁdential information and sensitive discussions are
best handled elsewhere.

To get things going, I propose that we allow access to those on the DOMFaculty mailing list.
